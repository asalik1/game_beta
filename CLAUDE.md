## Code layout (see CODING_GUIDELINES.md §38)
- Tuning knobs → `balance.gd`; data tables stay in domain files (classes/items/story). Never inline a bare tuning number.
- Docs split (2026-07-06): balance/pacing round narratives go in `BALANCE_HISTORY.md` (newest at TOP of the tuning list); `DESIGN.md` holds only current decisions + distilled standing rules — never append round-by-round history there.
- Big node classes are inheritance CHAINS (verbatim moves, calls flow derived→base, all vars in the base layer):
  - Game: `game_base` (state/flags/convo/lookups/fx) ← `game_world` (graph/rooms/walls/spawning/gates) ← `game_flow` (deaths/loot/chapters/settings/terrain events) ← `game.gd` (boot + per-frame).
  - Player: `player_core` (state/stats/gear/progression) ← `player_combat` (targeting/hit/shared juice + shared primitives) ← `player_kit_{warrior,archer,mage,assassin,paladin,warlock}` (one file per class: `_use_<class>` dispatch + its abilities) ← `player.gd` (dispatch/survival/per-frame). Primitives shared by several kits (`_dash_strike`, `_melee_arc`, `_mist`, `_beam_fx`, `_grant_stab_surge`) stay in `player_combat` — calls only flow derived→base.
  - Tests: `tests/test_base` (helpers) ← `tests/test_ch1` ← `tests/test_ch2` ← `autotest.gd` (entry + systems tier).
- Self-contained UI screens = static modules in `scripts/ui/` (dev_panel, codex) taking the Menus instance.
- New `class_name` script → run `--import` before any headless run.
- The in-game **codex** (`scripts/ui/codex.gd`) is the player-facing reference for monsters/bosses/terrains/gear — it goes stale silently. Whenever you add player-facing content or a feature, ask whether the codex should reflect it, and if so update it in the same change. It reads `Story.ALL_ENEMIES`/data tables directly, but a few hand-maintained parallel lists still gate it (e.g. `menus.gd` `BOSS_KINDS` decides monster-vs-boss bucketing) — update those too, or a new boss lands in the wrong bucket. Layout since 2026-08-15 = rail of sections (`UICodex.SECTIONS`) + filter chips + ledger/detail; a new section is one SECTIONS row + a `_rows`/`_detail` (or page) builder, and every legacy `open_codex("<tab>")` id routes through `_resolve()` — extend that, never fork the panel. Reference prose lives under Field notes (`NOTE_PAGES`), not above a shelf.

## Testing — ALWAYS in this order
1. Compile gate first, every time (`test_quick.bat`/`test.bat` run `check_compile.gd` first). Never invoke the test scene directly: one parse error anywhere makes the suite script fail to compile and the headless engine idles FOREVER (a zombie that looks like a slow run). The gate catches it in ~3s with the real error.
2. Iterate with `test_quick.bat` (~15s): gate → boot → one class kit → systems → UI smoke → pause menu.
3. `test.bat` (full suite, minutes; plays both chapters end to end) must be green before staging.

- `preflight.bat` — the traps below, mechanized: stale/forgotten `--import`, codex/BOSS_KINDS staleness, unregistered content modules, diff-scoped balance-number + CONNECT_DEFERRED lints, new shot rig not `extends ShotRig`. Run it before staging; every finding prints its one-line fix.
- `python tools/safe_commit.py -m "msg" <your paths>` — the serialized-commit etiquette as a guardrail: path-scoped commit that lists sibling-staged work instead of swallowing it.
- `python tools/sync_mobile.py` — mobile drift report; `--apply [--gate]` performs the re-sync ritual from `mobile/README.md`.
- **Headless Codex (`codex exec`, the default generated-art lane): calling guide = `C:\Users\asali\Projects\CODEX_HEADLESS.md` (Projects root, shared by every project on this box: binary, call, all flags, machine limits) + `tools/CODEX_HEADLESS.md` (the MMO layer: runner, drivers, vet/install).** The binary's install dir is re-hashed on every app update — resolve it (`python tools/codex_bin.py` / `Resolve-Codex` in `run_codex_batch.ps1`), never hard-code it; prompt goes on STDIN; on this shared box run image batches serial + RAM-gated (`run_codex_batch.ps1 -MaxParallel 1 -MinFreeGB 1.3`), never beside a Godot suite (a parallel batch + suite OOM-crashed the host 2026-08-17).
- `python tools/art/verify_art.py <base>` — post-install sprite checks (strip geometry, 8-dir completeness, green-bleed, stale import, and in-cell content gates: anchor drift/ghost chunks/edge cuts/clip-vs-idle body scale + **HEROBODY** hero frame-0 scale-lock shrink).
  - **HEROBODY vs CLIPSCALE (added 2026-08-23):** CLIPSCALE models the ENEMY renderer (median body / cell). HEROES render differently — `player_core._measure_hero_frame` locks a clip's on-screen scale to FRAME 0's CONTENT bbox and plays the whole clip at it, so a clip whose REST pose already raises a weapon (frame-0 content > body) renders the body small for the entire clip (the archer-multishot 0.85× shrink CLIPSCALE structurally cannot see). HEROBODY flags a hero action clip whose frame-0 body renders <0.90× the idle's. A neutral rest frame reads ~1.0 and a legit crouch/lunge still starts neutral, so both are spared (0 FP across the 6 base classes + 5 skins).
  - **The eyes-only drift class has NO geometric gate — the net is a VISUAL QA artifact + agent review.** Face-fidelity drift (a fatter/blurrier face in action frames), a shield/armor detail that morphs frame-to-frame, a cape that flips sides — all pass every geometric check; the *drawing* is inconsistent. verify_art cannot catch these and a sharpness/consistency proxy false-positives on real motion. So a skin/class regen MUST emit a per-clip contact sheet (idle + action peak frames, feet-aligned + face crops) and an AGENT must review it before install. An AI reviewer catches "her face got fatter"; a number can't. Don't rely on the owner's eyes as the first line. **The full reusable workflow — dedup-scope → one review agent per subject over EVERY clip×dir×frame → orchestrator verifies each flag — is `tools/art/DRIFT_AUDIT.md` (covers heroes/skins AND the boss/mob adaptation: enemy render path = CLIPSCALE not HEROBODY).** Established 2026-08-24; the known drift catalogue (fire-on-move clips are the systemic weak point; un-regenerated clips carry the face-softening family; single-direction off-model art) lives there.
  - **WARN triage — FAIL is the bar, not WARN (investigated 2026-08-23).** The six BASE heroes throw a large, standing pile of WARNs that are NOT defects — the gate has no way to whitelist intentional content, so it flags it every run. All three benign categories, confirmed by rendering the flagged pixels on grass + overlaying them on the sprite:
    - **BLEED** on base heroes ≠ green keying rim. It's soft-alpha FX (the archer's cast/ult IS green Arrow-Storm magic; every class's ult/cast auras + glows) plus green-CLOTHING edges (the archer's green cloak). The BLEED counter is colour-blind (any `0<a<255` pixel), so green *content* inflates it; a band-normalize/upscale multiplies the same FX/cloak edge pixels and the raw count rises with zero new bleed. The real-bug discriminator is a green RIM hugging the silhouette (`G>max(R,B)+20` massed on the body outline) — on the base heroes that rim is absent; the green sits on the FX cloud and the cloak, and on a grass background there's no halo.
    - **STRAY** on base heroes = FX props the game does NOT re-spawn: the warlock's floating flaming SKULL (his signature, every frame), the warrior's flaming-sword blade/trail, the archer's green cast-motes. Distinct from a baked *projectile* (which the STRAY rule is really aimed at) — leave these.
    - **EDGECUT — OVERRULED 2026-09-06.** This used to read "the weapon reaching the cell edge at the extreme of the arc, not a clipped body". The owner rejected that: *"not true / if a weapon is cut off outside the frame that is a regression too"*. A figure and everything it carries must fit its cell, on every clip. `verify_art` now FAILs EDGECUT on ANY strip once the longest CONTIGUOUS run of silhouette on a boundary column reaches 18% of the body height (a 1-2px antialias graze is not a run, so it stays quiet). Sprites that fill their frame BY DESIGN — ground/canopy/wall tiles and projectiles — are excluded by class, not by judgement. 58 strips already cut on main (mostly legacy 4-frame death strips whose lying body reaches the boundary) sit in `EDGECUT_KNOWN` as DEBT so a clean tree reads 0 FAIL; delete a name from it the moment that art is re-made.
    - Baseline as of 2026-08-23: base heroes = **0 FAIL, ~261 WARN** (208 BLEED / 28 STRAY / 25 EDGECUT); the 5 in-scope elite skins = clean `VERIFY OK`. Don't re-investigate or "fix" these WARN categories on the base heroes — only act on a NEW **FAIL**, or a WARN that leaves these three buckets (e.g. a real body green-rim, a butchered/PARTIAL frame, an anchor/scale/FEETSLIDE hit).
    - **CORRECTION (2026-09-03): the "no green rim on base heroes" finding was scoped to cast/ult.** A corpus scan (`tools/art/despill_rim.py --scan`, rim-band green with an EMPTY interior = halo, not design) found a real #00FF00 keying ring on all 19 `warlock_attack*`/`attack2*` strips — a design with no green in it at all — plus 44 mobs/NPCs/props. All despilled; the scan now returns 0. Re-run the scan after any keyed install; the fixer is rim-band-only so it cannot dull green garments, and it refuses a sprite whose green is mostly interior.
- **Screenshot rigs: never write a standalone one (2026-08-15).** Twenty-three `game/shot_*.gd` files are copies of the same 25-line boot/`_shot`/quit boilerplate, none with a watchdog, muted only by convention. New rig = `extends ShotRig` (`scripts/dev/shot_rig.gd`: `boot()`, `shot()`, sim-clock waits, `arg()`/`flag()`, Master-bus mute, `--timeout=N` watchdog) + `_ready()` of steps + `finish()`; run it — and every legacy rig — through `shot.bat <rig> [--timeout=N] [rig args]`, which injects `--audio-driver Dummy`, compile-gates the rig script (check_compile's default walk skips `game/` root: a parse error there = a window that idles forever), and hard-kills a hung engine. `preflight` FAILs a new rig that doesn't extend it and WARNs on an edited legacy one (convert on touch). Worked example: `shot_fx_series.gd`; the map: `tools/INDEX.md` "In-engine shot rigs".
- **Screenshot verdicts (2026-09-08):** the runner rejects `SCRIPT ERROR`, parse/assertion failures, unexpected engine `ERROR:` lines and watchdog errors from either output stream even when a rig prints `RIG DONE` and exits zero. Modern ShotRig scenes must print a valid completion marker; legacy rigs retain their exit-code path. `tools/tests/shot_verdict_tests.ps1` covers this contract with 18 fixtures, including closed-ENet and physics errors. Only the established renderer texture-RID and RenderingServer shutdown diagnostics are exempt; the headless suites keep their own stricter resource-leak gate.
- **Windowed shot rigs (`shot_*.tscn`, `qa_skins`, anything not `--headless`) run MUTED: always pass `--audio-driver Dummy`.** They boot the real game with music + SFX on the owner's shared machine; an unmuted rig blares through his speakers mid-session (owner ruling 2026-08-15). Headless suites are already silent.

## GDScript traps (each has bitten us) — review-time deep list: `CODING_GUIDELINES.md` §38
- `var x := obj.method()` on a loosely-typed obj (or any Variant expression, e.g. `Dictionary.get`) = PARSE ERROR "cannot infer type". Annotate: `var x: float = ...`.
- New `class_name` → `--import` first or headless silently hangs.
- Labels inside HBoxContainer collapse to one char per line without `custom_minimum_size`.
- Multiline lambda: following call args must sit on the SAME line as the lambda's last statement.
- Tests waiting on timed effects must poll wall-clock (`await create_timer(0.2)`) — frames race ahead headless.
- Autotest sections SNAPSHOT + RESTORE shared state (flags, resonance, standings); never `.clear()`. Two corollaries, both learned from one flaky capital run (2026-07-26):
  - **Restore on the FAILURE paths too.** `_fail` only QUEUES `quit(1)` — the suite keeps running to the end of the frame, so the next section still executes and reads whatever the failed one left behind. A mid-city failure stranded `chapter_id == "capital"`, where `shop_markup` answers a flat 1.0, and the road-markup section then reported a second, entirely bogus failure. Put the assertions in a helper and the restore in its caller, so all ~40 exits pass through it.
  - **Never assert against state an earlier section accumulated.** A content-tier section inherits a whole campaign of loot, gold, resonance and bag capacity — all of it loot-luck. The capital's lapidary quest asserted its kit landed in the bag, and a full bag legally mails the kit instead: pass or fail came down to whether a bag DROPPED that run. Control the precondition (lend a bag, pin the shard) or the assert is a coin flip.
- **HDR2D screenshot color (2026-09-08):** viewport readback is LINEAR on Forward+/Mobile. `ShotRig.capture_image()` converts float samples to sRGB before quantizing once to PNG bytes (quantizing linear values first bands dark panels); Compatibility is already sRGB and skips that step. Raw legacy HDR screenshots look artificially dark: never regrade game assets against those captures. Use the shared rig, and validate renderer changes with the known-color swatch in `shot.bat floorfield --compare`; `--mobile --renderer=gl_compatibility` checks the handheld renderer path on the development host.
- canvas_item shader `fragment()`: `COLOR` arrives PREMULTIPLIED (modulate × TEXTURE sample). Writing `COLOR = result * COLOR` multiplies the texture in twice — everything darkens and "brighten" shaders read as darken (phantom_charge was bitten; owner saw "only gets darker"). Reuse ONLY `COLOR.a` (silhouette.gdshader convention).
- `Environment.adjustment_contrast` with `viewport/hdr_2d` runs in LINEAR light: it pivots on 0.5, and a dark floor sits near 0 there — contrast 1.06 HALVED the keep floor's brightness (gameplay-polish rig 2026-08-18). Leave contrast at 1.0; use saturation/brightness only, and judge any whole-frame grade in-game, never from the numbers.
- Spawning an Area2D + CollisionShape2D (Chest/Pickup/Projectile) from inside a `body_entered`/`area_entered` handler = non-fatal "Can't change this state while flushing queries" engine error (`area_set_shape_disabled`) — the new shape's enter-tree hits the physics-flush guard. Connect physics signals with `CONNECT_DEFERRED` or `call_deferred` the spawn (chest open + projectile ricochet were bitten).
- `draw_colored_polygon` on a SLIVER (near-collinear points) = random non-fatal "Invalid polygon data, triangulation failed" spam: the triangulator picks winding from a float32 shoelace over RAW coords, so a sliver's sign is rounding noise at world-scale coordinates — coordinate-dependent coin flip, NOT deterministic per shape (knife-trail fold-back miters were bitten). Pre-check `Geometry2D.triangulate_polygon(p).is_empty()` and skip — the exact C++ path behind the error, and everything it rejects is sub-pixel (the `_poly` guard in player_combat.gd).
- **In co-op, the tree pause is NOT an input gate.** `request_pause(true)` NO-OPS online (`game_base.gd`, §5.4 — a shared world never pauses), so anything leaning on the pause to stop input/processing keeps running in a session. Menus, dialogue and choice prompts all pause solo and none of them pause online. Gate on the OVERLAY STATE instead — `menus.is_open()` / `hud.dialogue_active` / `hud.choices_active`, the guard `game.gd`'s tap-to-talk already uses. The touch HUD had no `process_mode` override and only checked `state == ST_PLAYING` (there is no `ST_MENU`), so its joystick — the whole left half of the screen — stayed live UNDER every menu and a drag walked your hero mid-fight. Note the shape of the miss: it was invisible in BOTH cheap tests (solo-on-phone pauses; co-op-on-desktop has no touch HUD) and only existed in the mobile × co-op cross-product. When a feature is platform- or session-conditional, ask what its gate is in the OTHER combination.

## Machine RAM is tight (~10GB) — tool-process hygiene (2026-08-23)
- This box has ~9.8GB physical RAM and the BASELINE load already fills it: Claude Code + its MCP servers ≈ 3GB (22 procs — MCP servers orphan on restart; 3 duplicate `pixelforge-mcp` copies seen), browser ≈ 1.2GB, Windows (svchost + Defender + compression) ≈ 1.4GB. That leaves ~1GB free — nothing has headroom. This is WHY image batches run serial + RAM-gated and never beside a Godot suite. But be precise about WHAT is heavy: **a single `codex exec` image gen is API-side and costs only ~250MB local (measured 2026-08-24) — it is NOT a machine-killer and a single serial job runs safely even at ~1GB free.** The RAM risk is PARALLELISM (several gens at once) × a co-resident **Godot suite** (each Godot instance is the real GB-scale hog). So `-MaxParallel 1 -MinFreeGB 1.3` guards against *stacking* jobs and firing next to a suite — don't read it as "Codex is a spike" and refuse a single gated gen. (PixelLab local footprint unmeasured; don't assume it's the same.) A Claude restart clears orphaned MCP servers; closing browser tabs frees ~1GB.
- **Prefer the Bash tool over PowerShell.** PowerShell tool calls can leave lingering `powershell.exe` processes (7 orphans spanning 2 days seen, ≈0.45GB). Use Bash for process/file ops (`taskkill //F //PID <n>` cleans strays); reserve PowerShell for genuine cmdlet needs, and consolidate into ONE call rather than many.

## Icon fidelity — authored resolution ≠ render size (owner ruling 2026-08-21; agents keep tripping on this)
- Player-facing icon families are **DUAL-RES**: a high-fidelity master for the codex/detail views + a downscaled gameplay copy for the bag. The **128px painterly master is the FIDELITY BAR** — match it, not a flat/pixel style, unless the owner says otherwise. Reference tiers: **gear** = `assets/icons/codex/<shape>_<grade>.png` @128px (codex, via `Art.codex_item_icon`) + `assets/icons/<name>.png` @32px (bag); **class splashes** ~235px authored → render ~100px in-game (~2.35× — the owner's "renders nicely" benchmark).
- **THE TRAP:** authoring a family at **32px only**. It looks fine in a 32px bag slot, so it passes a quick check — but every larger surface (codex ~28–128px, the detail popover header 40px) UPSCALES it to mush, and it reads as low-fidelity beside the 128px gear. **Gems shipped 32px-only (2026-07-30) and were the 2026-08-20 visual-review's one solid asset catch for exactly this.** When you regen an icon family: author at the 128px gear bar, store dual-res, and load the 128 in large contexts. Verify the fidelity numbers (stored res vs on-screen render px) BEFORE designing — the owner asks for this by name.
- **This generalises past icons to ALL world/character/codex art (owner ruling 2026-08-24): a master should be ≥2× its on-screen render size.** The auditor is `tools/art/fidelity_audit.py` + `game/fidelity_dump.gd`; the current findings + prioritised re-art list live in **`FIDELITY_AUDIT.md`** (root). Bar = the base classes (render 99px from 235px = 2.35×). Standing findings: the **5 enhanced-base skins PASS (2.37×)** but the **18 legacy skins are ~1.2×** (the planned regen quantified); trees/large props + one npc (`pilgrims_schism`) + `choir_censer` (a boss-summoned add) are the other real re-art targets. Unplaced+low-fi mobs get DROPPED, not re-arted (`bat`/`direbat` gone 2026-08-24).

## World props — style + motion contract (owner ruling 2026-08-18, after a day of "shifts / dims / cartoonish" flags from play; review-time checklist: `CODING_GUIDELINES.md` §40; the polish effort's board = `POLISH_TASKS.md`, its generation lane = `tools/art/style_unify/`)
- **One style.** Every world prop matches the cast: painterly, soft-shaded, NO black outlines, muted palette, top-down three-quarter, light top-left. A hi-res canvas is NOT a pass — a 1024px cartoon is still a cartoon (cactus2, tree_teal2, grave_cross all passed the resolution audit). Regen briefs name a painterly SIBLING as the style ref and the old asset only as the SUBJECT (silhouette/footprint/colour identity); judge the result on a contact sheet BESIDE its siblings (`scratchpad`-style sheet, or `tools/art/asset_gallery.py`), never against the asset it replaces.
- **Animate in place.** Frames never translate the object. Rigid props (furnaces, wells, shrines, rigs, pools) keep a byte-stable silhouette — colour-only motion (glow pulse, ember flicker), bbox/baseline/centre drift 0; only fire, cloth and foliage may change silhouette, and then anchored on frame 0's baseline. Wind sway is an ALLOW-list of vegetation (`_wind_scenery`), never "everything that isn't a building". Hazard pools stay put (`Balance.HAZARD_POOLS_DRIFT`). Anything that swings/pendulums needs authored frames with proper easing or no animation at all — a 4-frame swing reads as fake.
- **Dim, don't strobe.** A prop should look STILL at a glance and alive on a second look. Luminance swing ≤ 10-12% for glows/pulses (`derive_prop_anim.py --amp 0.10`), ≤ 25% for open fire, never on the whole sprite (bright/warm pixels only). The 0.35 default that looked "visible" on a contact sheet strobes in-game.
- **A LOCOMOTION body must fit inside its cell — EDGECUT is a FAIL there, not a WARN (owner catch 2026-09-06: "slag hound its legs appear cut off").** Six quadruped/arachnid walk regens and two recentred grove_horror strips shipped with the hindquarters or tail sliced flat against the cell boundary, and every one of them sat in `verify_art`'s WARN pile — where CLAUDE.md's own triage says EDGECUT is the benign weapon-at-the-extreme-of-a-swing class. That triage is right for an ACTION strip and wrong for a walk or an idle: the renderer normalises a locomotion strip by its own cell, so anything outside it is simply gone. `verify_art` now FAILs when the longest CONTIGUOUS run of body on a boundary column is >= 18% of the body height on a `*_walk*`/`*_anim*` strip (a sliced hindquarter measures 19-50%; a leg, tail or flame TIP measures 2-14% and stays a WARN). Four strips already cut on main are listed in `EDGECUT_KNOWN` so a clean tree reads 0 FAIL.
- **A mean-statistic colour match is not a colour fix (tried and reverted 2026-09-06).** A regenerated walk can come back a different COLOUR from its idle while its luminance matches, so the luma tone-match cannot see it (blightwolf 39 degrees olive to green, void_hound 35 degrees blue to violet, wolf 20 degrees). The obvious repair -- rotate the strip's weighted-mean hue onto the idle's -- is WRONG for this cast: these bodies are a large desaturated mass carrying a small saturated ACCENT, so the mean is dominated by the mass and the rotation drags the accent somewhere else. Measured 0 degrees of error afterwards while blightwolf's lime veins had turned brown. `palette_grade.py` deliberately has no `--hue`. If a strip's colour is wrong, fix the ACCENT or re-roll it, and judge the result beside the idle before install.
- **Never hand-assemble generated art (owner ruling 2026-09-06): "ai is incapable of slicing images and piecing them together ... which is horrible and should never be done".** The gait lane's row-slicing is the whole reason the mob walks came back looking pieced together (skeleton, skeleton_rogue). A generated row may be sliced ONLY when every figure is cleanly separated and the result is judged frame-by-frame beside the outgoing strip; compositing a limb from one frame into another, splitting touching figures, or reconstructing a cycle from mirrored halves is out. If a row does not slice cleanly, re-roll it — do not repair it.
- **A regen must beat what it replaces, or it does not ship.** Reverting to the outgoing strip is always available and is the right call when the new one is cut, off-model, or reads worse — a stiff 4-frame walk beats a chopped body. `git checkout <base-ref> -- <path>` after backing the regen up in `art_src/_backups/`.
- **A strip can also move TOO LITTLE (2026-09-06).** Five shipped `_anim` strips were DEAD: the motion's colour mask matched almost nothing in the art, so the prop animated nothing at all (`shimmer` on olive sludge, `swirl` on pale-blue light, a canopy strip that was four copies of the static). `derive_prop_anim` now prints the mask coverage and warns under 1%, `audit_prop_anims` FLAGs `DEAD` under 0.5% of the body changing, and props that are inert by design (empty pan, dark well, unlit firepit) sit in `NO_MOTION_OK`. Pick the motion the ART supports: `flicker`=warm fire, `shimmer`=blue water, `flow`=any pouring liquid (olive sludge too), `pulse`=a glow (glow-only since 09-05), `swirl`=void/arcane energy, `sway`=a rooted canopy, `wave`=hanging cloth.
- **Gate every strip you touch:** `tools/art/audit_prop_anims.py` (frames/canvas/per-frame drift + amp) + `verify_art.py`; a NEW rigid animated prop goes into autotest's `full_prop_anims` contract (frame == static canvas, baseline ≤1 / centre ≤2). Contact sheets and metrics do not replace watching the loop: run it in a shot rig at 1x (`shot.bat polish --gif`) before calling it done — a subtle loop that looks static on a sheet is correct.

## Required per-class animation clips beyond the standard set (so a regen knows what to produce) — 2026-08-23
Some abilities need EXTRA clips on top of anim/walk/attack/attack2/dash/cast/ult/death. A class or skin regen MUST produce these or the ability silently falls back to a worse pose. Both are art-driven (no strip = the fallback), so they're easy to forget — hence this manifest.

- **Fire-on-move (`<base>_attack_walk[_<dir>]`)** — a walk cycle that fires the basic mid-stride, so spamming a low-cd RANGED basic WHILE MOVING doesn't lock the standing pose sliding over the floor (`player.gd` `walk_fire`; a mid-cycle re-cast lets the stride finish). Needed by the ranged spammables ONLY:
  - mage **Firebolt** (a1=attack), warlock **Shadowbolt** (a1=attack), archer **Quick Shot** (a1=attack), assassin **Fan of Knives** (a3=attack2).
  - NOT the melee 3-way basic — the assassin STAB keeps its attack/attackb/attackc alternation while moving (gated by `slot=="a1" and _clips.has("attackb")`, which only excludes the assassin).
  - **HOW TO GENERATE (the technique that finally worked, owner 2026-08-23): it's the WALK clip + a firing arm — do NOT author a walk from scratch.** Give the character's EXISTING `<base>_walk_<dir>` strip as the image ref and instruct: "reproduce this exact walk — same leg cycle/stride/crossing, same garment — change ONLY the free hand to fire the basic once." A from-scratch walk brief (however detailed the per-frame boot storyboard) kept gliding or failing to cross the legs; referencing the real walk carries its crossing gait for free. Keep the brief SHORT — the walk ref IS the leg spec.
  - Contract: 8-frame walk+fire; feet PLANTED (no in-cell slide → FEETSLIDE); the garment stays CLOSED and design-accurate (NO slit, NO exposed legs/bare skin — the walk reads through the BOOTS alternating below the hem + the hem swaying, exactly as the walk clip does); NO baked projectile/flame on the sprite (the game spawns it — a small warm spark shares the mage's skin/gold palette and is un-maskable by colour except the bright-yellow core, so keep it out at gen time). Author S/E/N; E→SE/NE; **left MIRRORS right** (W/NW/SW = mirror of E); flat = S. Build lane: `scratchpad/attack_walk_codex.py`.
  - **`attack_walk_b` — the alternate variant (owner 2026-08-23).** Fire-on-move ALTERNATES `attack_walk ↔ attack_walk_b` each fresh moving-basic cycle (player.gd `_walkfire_swing`), like the melee attack↔attackb, so spamming while moving doesn't replay one clip. Produce it with the SAME walk reference — only the FIRE motion differs from the primary (warlock: two-hand shove vs one-hand thrust; mage: free-hand rising flick vs level thrust, staff hand kept clearly separate; assassin: sidearm flick vs overhand throw). **NOT the archer** (owner 2026-08-23): a bow draw has ONE proper form, so the archer has no `_b` — it plays the primary every cycle. When a `_b` would confuse the silhouette (e.g. the mage's casting hand reading as the staff hand), keep the two hands clearly separate or skip the variant. Build lane: `attack_walk_codex.py … --b`. Art-driven: no `_b` strip = the primary plays every cycle.

- **Melee swing alternation (`attackb`, and `attackc` for enhanced variants)** — melee basics cycle multiple authored swings per cast (`player_core.gd` `_alt_basic_clip`: attack→attackb→attackc) so Cleave / Smite / Stab don't replay one motion. Which classes ship which:
  - **warrior, paladin, assassin** carry `attackb` (2-way minimum). Ranged classes (mage/archer/warlock) have only `attack`.
  - **3-way (`attackc`)**: base **paladin**, warrior **emberbound_heir**, assassin **erased_name** (owner 2026-08-22 — the enhanced variants). `attackc` is a DISTINCT 3rd motion (a rising uppercut), not a recolor of attack/attackb. autotest `_test_swing_alternation` expects 3-way when a body ships an attackc.

## Generated art tool authorization
- **NEVER assume PixelLab is authorized. PixelLab may be used only when the owner explicitly authorizes PixelLab for the specific task.** Existing PixelLab assets, PixelLab helper scripts, character metadata, or a matching PixelLab workflow elsewhere in the repo do not grant permission for a new generation.
- When an agent has a built-in image-generation/editing tool (for example, ChatGPT/Codex image generation), that built-in tool is the default for generated art unless the owner explicitly requests or authorizes another generator.
- This rule applies even when another generator appears technically better suited. If the built-in tool cannot meet the requirement, stop and ask the owner; do not silently switch tools or spend external generation credits.

### Codex built-in ImageGen walk-animation observations
- For bipedal characters, the built-in ImageGen tool often fails to preserve a fluid left/right leg cycle. A real same-colored leg crossing over the other in one passing frame can create a convincing walking illusion; keep that crossing to one or at most two frames rather than making every frame crossed.
- If ImageGen repeats nearly identical crossed poses, give each cell an explicit foot-position storyboard instead of only asking for "alternating legs": use a wide split, a tight crossover, a second crossover with a different spread and the opposite leg emerging, then the opposite wide split or a subtle toe-off. State that frames 1, 3, and 4 must have visibly different lower-body silhouettes. (Tried on the Wild Fang Raider 2026-08-14 and again 08-15: the 4-cell 2x2 kept coming back with the SAME leg leading in both stride cells and the body ~11% short — the owner still called the walk bad.)
- **What actually fixed the Wild Fang Raider walk (2026-08-15): ONE ROW of EIGHT figures, each frame labelled with its gait phase** (near-foot contact / load / far leg passes / reach, then the same four for the other leg — the pipeline doc's "legs do not alternate" remedy). The row came back with 8 distinct poses, constant body height and one ground line; installed as an 8-frame strip (the engine's strip reader is frame-count agnostic — width/height — so 8 is fine; at the 2x walk clock the loop runs 0.67 s). Prefer this over 4-cell 2x2 for any bipedal walk. Ask Codex to report leg-lead per frame in its final message; it is a candid critic of its own output.
- **Write every identity description FROM the idle sheet, never from memory or an audit's paraphrase (2026-09-03).** Three of fifteen boss/mob regen rows drifted for exactly this: a skeleton got a shield the idle never carried (twice — the pilot and the batch), the winged flame-skull echo came back as a plain hooded shroud, korrag lost his lightning arcs. The generator reproduced the prose faithfully; the prose was wrong. Look at `<base>_anim` frame 0 and list what is actually there (what is in each hand, what is NOT there) before writing the brief.
- **A BACK-view regen never gets the outgoing strip as a reference** when the defect IS the view (front art wearing the N name): handing it back re-seeds it. `gait_briefs.py` drops it automatically on `facing: n`; the identity ref stays the front idle with the front-only parts NAMED as forbidden.
- **Row briefs must say every figure is the SAME size** ("do not crowd two small figures into one cell; make the image wider"). Three rows came back with undersized figures crammed into one cell before the brief said so; `install_gait_row` refuses a speck cell rather than ship a blinking near-empty frame.
- **Cells ≥ 900px: request a two-row GRID, not a row (2026-09-04).** A 6-figure row comes back ~2100px wide (~400px figures), so a 920/1084px boss cell forces a 1.4-2.2× upscale at install (stormmouth/nullwarden N shipped soft the first time). Ask for TWO ROWS of THREE ("each figure roughly 900px tall") and flatten with `tools/art/grid_to_row.py`; the same rows landed at ~870px, installed at 0.65-1.07×.
- **A facing column authored FRONT-ON (the base mage's whole E column, the warlock's 3/4-front walk E) is fixed with `tools/art/profile_clip_briefs.py`** (identity = front idle, view = a real profile sibling, action = the old clip). When a base WALK is regenerated, its `attack_walk_<dir>` was built ON the old walk (the walk-plus-firing-arm technique) and must be regenerated from the new one, or fire-on-move snaps to a different view mid-stride.
- Every ImageGen-keyed strip carried a dark-green antialias rim (`build_mob_walk_repairs.remove_green` now despills the 2px edge band); a strip that "looks fine" on a dark contact sheet can still ring green over grass — check `G > max(R,B)+20` counts on the rim, not just the semi-alpha BLEED gate.
- The tool is generally more reliable for non-bipedal walks (for example, spiders and wolves), and for characters whose locomotion does not expose a conventional leg cycle: robes can communicate motion through cloth flutter, and floating characters can use body/cloth drift.
- For bipedal sheets, prompt for fixed torso/pelvis anchors, a shared foot baseline, compact stride, held-weapon/upper-body continuity, and explicit negative constraints against recoloring legs, detached feet, duplicated frames, and high-knee marching. Inspect the generated sheet before installation and run `tools/art/verify_art.py <base>` afterward; anchor drift can still remain even when the sheet looks visually centered.

## PixelLab characters — regenerating an EXISTING one (deep dive: `tools/art/PIXELLAB_BOSS_EDITS.md`)
- **Authorization gate:** this section applies only after the owner has explicitly authorized PixelLab for the current task. It is not permission to choose PixelLab.
- **RULE: before you regenerate, re-roll, or tweak an existing PixelLab character (boss/hero/skin), ALWAYS read its export metadata FIRST.** Download the zip (`curl -H "Authorization: Bearer $PIXELLAB_SECRET" https://api.pixellab.ai/mcp/characters/<id>/download -o out.zip`) and read `metadata.json` — it stores the ORIGINAL creation `prompt` (plus size, `template_id`, view). Regenerate from that EXACT prompt and change ONLY the clause the owner flagged.
- **Never invent a fresh description from a screenshot or memory** — it silently drifts the design (proportions, palette, silhouette) even when the fix was one word. `get_character` does NOT return the creation prompt; the zip's `metadata.json` is the only source of truth.

## PixelLab characters — new generation workflow (prompt-craft cases: `tools/art/PIXELLAB_PROMPT_LESSONS.md`)
- **CHECK ALL 8 ROTATIONS before generating animations.** After a character body is created, visually inspect every direction (S, SE, E, NE, N, NW, W, SW) for consistency — same proportions, same gear, same silhouette. v3 mode frequently produces inconsistent north/west directions (wrong body shape, missing equipment, different outfit). If any direction is broken, re-roll the body first. Generating animations on a broken body wastes hundreds of generations.
- **Heroes use v3 mode (NOT pro).** The gold-standard assassin and warlock were both v3. Pro mode produces stocky proportions for visible-face characters. The `style: -, -, -` field in `get_character` appears in BOTH v3 and pro — it cannot distinguish modes.
- **Standard mode is useless for proportions testing.** Its template skeleton produces chibi proportions regardless of description. Only useful for testing color palette and design elements.
- **Description formula (proven on assassin):** archetype first → every piece of gear described precisely → body type ("lean and gaunt" / "lean and tall") → art mood ("muted dark palette, somber dark fantasy") → explicit negatives ("no hood", "no smoke"). Leave no room for the model to improvise.
- Worked example (2026-07-12): owner said Vess should have "no smoke from mouth". The metadata prompt literally contained `faint blue-white keening light at the mouth` — the fix was deleting that one clause from the original prompt, not writing a new banshee description.
