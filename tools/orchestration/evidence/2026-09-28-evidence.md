# Architecture evidence — Crownless orchestrator session 2026-09-28

Source data for evaluating the multi-agent architecture. Numbers were collected from run receipts,
Workflow usage reports and glock logs. "~" means an approximate figure read from notifications.

## Architecture v1 as run
- Root orchestrator: Claude Opus 5.5, one long session. It wrote briefs, launched implementers from its
  own background shell, launched review Workflows, integrated, ran batch gates, and handled ~100
  notifications and incidents. It never implemented.
- Ideation: 4 Claude scouts (Workflow, 1.33M tokens, 16 min, 29 proposals), Codex read-only (8 min, 10
  proposals), DeepSeek v4-pro agentic (7 min, 10 proposals), and later a second, narrowed Codex round
  (7 min, 6 combat bugs, all later confirmed).
- Implementers: Codex (gpt-6-astra, effort high) did 24 tasks (22 features + 2 merges). DeepSeek did 0
  (402 insufficient balance on its first implementation).
- Review: review_fix.js (3 read-only lenses → fixer → independent verifier, up to 2 rounds) or
  review_lite.js (1 combined reviewer → fixer → verifier). fix_verify.js resumed interrupted runs.
- Lanes: sparse git worktrees (~170 MB) with hardlinked assets and a junctioned `.godot`. Max 9 lanes;
  ~7 in flight at the peak.
- Heavy-run lock (glock): ONE headless Godot suite or rig at a time. A quick suite is ~3.7 GB RSS on a
  ~10 GB box, takes 2-3 min, plus queue wait. Later FIFO + per-lane fairness + --priority.
- Integration: squash-apply lane diff (git apply --3way), then batch gates: full desktop (~5-6 min),
  mobile sync + gate (~4 min), strict preflight (~4 min).

## Incidents (what went wrong)
1. 09:14: all 20,267 main assets were deleted through a junction by `git reset --hard` in a sparse lane
   whose skip-worktree bits had been cleared. Recovered from git in ~5 min. Fix: hardlink farm.
2. 07:34: DeepSeek balance exhausted by 3 agentic runs (full context resent every turn).
3. ~10:30-12:00: Claude session usage limit. ~8-9M subagent tokens were spent in 3.5 h with 6-7 review
   workflows in flight. The limit killed fix/verify agents mid-run and cost ~1.5 h of Claude work.
   Editing a workflow script made resumes re-run everything.
4. Lock saturation: queues of 8-17 waiters, individual waits of 600-1500 s. One agent queued 6 heavy
   jobs at once. Codex twice ended its turn or timed out while waiting, leaving work uncommitted.
   Lock starvation (no fairness) until a FIFO was added.
5. Git Bash rewrote `cmd.exe /d /c` into paths, so NOTHING ran and it reported exit 0 in 0 s: a false
   pass. Caught by a fixer, then fixed in glock (--suite + marker check).
6. Integration regression: T17 was verified on an older base. Combined with T16 on main, the full
   suite failed. Batch-only full gating found it late.
7. Two merge conflicts (T08, T13) in shared test files and docs (test_reward_feedback.gd, INDEX.md).
   `git apply --3way` left UU files in MAIN once; `git merge-tree` dry run later.
8. Orchestrator mistakes: editing a running bash script (integrate.sh), CRLF in a workflow file, a
   heredoc that broke glock.py for a minute, launching a job without `wait` (no notification).

## What worked
- Codex as implementer: fast (13-60 min), self-tests, commits on the lane, honest reports.
- Claude review loop: found real defects in every lane, including 6+ majors the implementer missed.
  Verifier rejection is where the loop pays off.
- Sparse lanes + hardlink farms: cheap isolation. After the fix, zero asset incidents.
- Scouts' JSON → mkbrief.py → brief with file:line evidence: fast task authoring.
- The orchestrator's own background shell for implementers: cheap and notification-driven.
- Batch integration gates (full + mobile + preflight ≈ 15 min) when the lock was free.
- Reviewers' "out of scope" notes became good follow-up tasks (T16, T20, T21, T22).

## Open questions for v2
- Is lite review (1 lens) as good as full (3 lenses) per token? Findings counts differ, but tasks differ.
- Which steps could run on cheaper models (Sonnet/Haiku) without losing catches? Examples: running
  gates, parsing logs, merges, mechanical fixes, the verifier's gate-running part.
- Would sub-orchestrators (lane managers) reduce root context load and notification handling, and at
  what token cost?
- How to cut lock demand: fewer redundant quick runs (implementer + fixer + verifier each run quick),
  targeted-module runs instead of whole tiers, or a second machine-level resource.
- How to prevent integration regressions cheaply (quick on main after each integration; rebase lanes
  before review; a nightly full run).
